How LETS Works

An authorization runtime for populations of agents that create more agents — and the accounting that keeps them bounded.

← Back to the register
The problem

An agent that can create another agent can create a thousand. If authority is a flag on an identity, every new worker is a fresh grant and nothing bounds the total. LETS makes authority a quantity instead of a flag, so delegation divides a fixed budget rather than minting a new one.

The runtime describes itself as governing “recursively created agents, replicas, delegates, robots, services, and other autonomous workers.” It is deliberately not an agent framework, a scheduler, a model host, or a transport. Your system keeps all of that. LETS answers one question, durably and with a signature: is this specific action, by this specific worker, right now, within what it was allotted?

Two ideas do the work. First, a worker holds a lease on a slice of a finite budget, and spawning a child moves budget out of the parent's slice — never out of thin air. Second, permission to act is not a boolean the agent can assert; it is a short-lived signed receipt the agent must obtain and hand to whatever actually performs the effect.

The vocabulary terms as the project itself uses them
Warden
A stable accounting replica with its own durable database and signing identity. It owns the ledger and answers every authorization request. This demo runs one.
Envelope
The bounded resource container, identified by (tenant_id, envelope_id, config_epoch). It has an ordered resource schema and a fixed genesis budget. Dimensions and units never change within an epoch.
Rights vector
The multi-dimensional quantity itself — a positional tuple of non-negative integers, 1 to 256 dimensions. Every allocation, residual, and cost is a vector of the same arity. Index order is the only thing tying a number to a meaning; units are declarative labels and LETS does no unit math.
Policy
Immutable and content-addressed: its sha256:… digest is derived from its contents, and each lease is bound to that exact digest. It declares the resource dimensions and a state machine whose edges are the permitted transitions.
Lease
A grant of authority to one subject: an allocation, the capabilities it may use, the policy it is bound to, its position in the lineage, a machine state, a sequence number, and an expiry.
Residual
What a lease has left — its allocation minus what it has spent and minus what it has escrowed into children.
Free pool
The warden's unallocated share. Root leases are cut from here.
Capability
A named permission carried on a lease, such as agent.research. A transition names the capability it requires. Capabilities not declared by the bound machine are rejected outright.
Attenuation
The rule that a child may only ever be narrower than its parent. Capabilities, allocation, TTL, tenant, envelope, epoch, and the exact policy digest are inherited or reduced — never widened.
Transition
An edge in the policy's state machine, with a source state, a target state, a required capability, and a cost vector that must be non-zero. Authorizing one debits the lease.
Receipt
The signed, short-lived, audience-bound artifact produced by a successful transition. It names exactly one executor and carries a single-use nonce.
Executor
The component that actually performs the effect. It verifies the receipt's signature and durably consumes it before acting.
Lineage
The parent-to-child ancestry of leases. Each grant carries its lineage_id, parent_id, and full ancestor path. Depth is capped at 64.

Every unit of budget sits in exactly one ownership class at any consistent moment. LETS states the invariant as:

The Conservation panel on the register checks this arithmetic componentwise on every refresh. It recomputes the equation from the raw /v1/invariants snapshot rather than reading the warden's own healthy flag, because a system reporting its own health proves nothing on its own.

Two rules keep the equation from being trivially satisfiable. Allocations and transition costs must each contain at least one non-zero component, which prevents cost-free authority trees and unbounded zero-cost receipt production. And the whole debit-and-credit for an operation commits in a single durable transaction, so a parent cannot be over-drawn by two children racing.

The four lifecycle seams where a host application calls the runtime
  1. Issue a root lease when a governed population is admitted. Rights are partitioned out of the warden's free pool.
  2. Spawn a child lease before creating a replica or delegate. The child's allocation is atomically subtracted from the parent's residual.
  3. Request a transition receipt immediately before a protected effect. This debits the cost, advances the machine state and sequence, and returns a signed receipt.
  4. Close, quiesce, renew, or revoke leases as the host lifecycle changes. Closing returns the lease's own residual.

Why the executor checks, not the orchestrator

The integration guide is explicit: “Checking a receipt only in the orchestrator is insufficient if an agent can reach the effect through another path.”

The receipt is bound to one named audience and carries a single-use nonce, and the executor durably records having consumed it. So the guarantee does not depend on the agent behaving, or on every code path remembering to ask.

What replication does not copy

Spawning a child in LETS means creating a new runtime identity under a declared capability, state, resource, policy, and lineage envelope. The docs are emphatic that it never means copying:

  • bearer tokens, private keys, or ambient authority;
  • a human or owner identity;
  • process memory, open sockets, or uncommitted work;
  • protected health information or other host-governed data;
  • audit signing secrets.

Artifact and state transfer stay on the host side. Only identifiers and evidence digests go into LETS requests. The adapter interface is shaped to make that boundary hard to cross by accident.

agent.publish is declared by the state machine but deliberately withheld from the root. That is what makes the escalation button a genuine attenuation failure — a child reaching for something real that its parent simply does not hold. Asking for a capability the policy had never heard of would fail for an entirely different reason and would prove nothing about attenuation.

The warden was initialized with a genesis budget of 10,000 actions and 1,000,000 tokens. Each root agent is provisioned 2,000 and 200,000 of those, so the free pool stays visibly non-empty beside the leased and consumed columns.

This is a development configuration

Loopback HTTP, a static bearer token, and the built-in file signer. LETS refuses all three under --production, which requires mTLS, a signed cluster manifest, and an external signer or HSM.

The parts this demo does not exercise are real features of the runtime, not gaps in it: executor-side receipt verification and replay rejection, lease expiry and reclamation, cross-warden transfers with exactly-once vouchers, branch revocation, and the hash-chained audit export.

That audit log is running underneath the demo the whole time. Every committed operation appends a signed, hash-chained record; refusals append nothing. You can read it at /api/audit, which also reports whether the warden considers the chain valid.
